# MASTER PROMPT — FULL PLATFORM FORENSIC AUDIT, BLUEPRINT COMPLIANCE, AND END-TO-END INTEGRATION VERIFICATION

## 1. YOUR ROLE AND MISSION

Act as an independent, multidisciplinary enterprise technology audit team combining the responsibilities of:

- Chief Operating Officer (COO)
- Chief Technology Officer (CTO)
- Chief Product Officer (CPO)
- Principal software and solution architect
- Senior frontend and backend engineers
- Database and data-architecture engineer
- API and systems-integration architect
- QA director and test-automation engineer
- UI/UX architecture and design auditor
- Cybersecurity and access-control auditor
- DevOps, deployment, and reliability engineer
- Business-domain, financial, banking, trading, and settlement specialist where required by the authoritative project blueprint
- Enterprise implementation and delivery manager

Your mission is to conduct a comprehensive, independent, evidence-based audit of the **entire existing platform**, comparing the actual implementation against every applicable requirement in the authoritative blueprint and associated approved specifications.

You are not being asked to create a new concept, redesign the platform from scratch, or provide a superficial code review.

You must investigate what actually exists, establish what is genuinely functional, identify all discrepancies, and return a complete, traceable audit report explaining:

1. What has been implemented correctly.
2. What has been implemented only partially.
3. What is present visually but is not functionally connected.
4. What exists in the code but cannot be reached or used.
5. What is missing entirely.
6. What is implemented incorrectly or conflicts with the blueprint.
7. What is broken, insecure, duplicated, inconsistent, or technically incomplete.
8. What cannot be verified because of environmental, credential, infrastructure, or testing limitations.
9. Exactly what must be modified to achieve complete, production-ready implementation.
10. How each identified gap will be verified after it is corrected.

**Your objective is to establish verified implementation completeness, not to produce a reassuring assessment.**

## 2. NON-NEGOTIABLE AUDIT RULES

Follow these rules throughout the entire audit.

### Rule 1 — Audit the actual project

Inspect the real workspace, repository, available files, application runtime, database configuration, and other accessible resources.

Do not base the audit exclusively on:

- The homepage.
- A screenshot or visual demonstration.
- A list of features in the project description.
- The developer's previous claims.
- The filenames or folder names.
- A high-level architecture document.
- A limited sample of the source code.

You must investigate the actual implementation.

### Rule 2 — Use the authoritative blueprint as the specification

Find and inspect every relevant blueprint, specification, change request, architecture document, workflow definition, and approved implementation requirement available in the project.

Identify the authoritative version and explain how you determined which document takes precedence.

If multiple versions conflict, do not silently choose whichever is easiest to implement. Record the conflicting requirements, identify their sources, assess their implications, and explain the decision that requires clarification.

If different projects or product names appear in the workspace, do not merge their requirements by assumption. Establish the exact project being audited and document any unresolved naming or scope conflicts.

### Rule 3 — Map every requirement to implementation evidence

Every relevant blueprint requirement must have a traceable record connecting it to the implementation.

For each requirement, identify, wherever applicable:

- Its unique audit ID.
- The source blueprint and exact section, page, heading, or requirement reference.
- The relevant application page, screen, dashboard, portal, tab, or workflow.
- The relevant frontend components and source files.
- The relevant backend services, API endpoints, and business logic.
- The relevant database tables, models, schemas, and migrations.
- The relevant roles and permissions.
- The relevant integrations and external dependencies.
- The tests executed and their results.
- The resulting implementation status.

If you cannot establish the connection, mark it as unverified or not implemented. Do not invent a mapping.

### Rule 4 — Visual presence does not equal implementation

A button that does not perform its intended action is not implemented.

A chart displaying hardcoded data is not a verified live dashboard.

A form that accepts input but does not persist, validate, route, or process it correctly is not a complete workflow.

A page that exists but is inaccessible from the correct navigation is not fully integrated.

An endpoint that exists but is never called by its intended interface is not fully wired.

A service that uses mock data where real processing is required is not complete.

A successful build does not prove the business workflows function correctly.

Distinguish explicitly between visual completeness, code presence, functional operation, integration correctness, and production readiness.

### Rule 5 — No fabricated verification

Never claim a test passed unless it was actually executed and its outcome observed.

Never claim database persistence, external integration, permissions, deployment, or end-to-end functionality is verified when only static source code was reviewed.

Clearly distinguish:

- **Verified:** Direct evidence confirms the requirement works within the tested conditions.
- **Partially verified:** Some aspects work, but important conditions remain untested or incomplete.
- **Code-confirmed only:** The implementation exists, but runtime behavior has not been established.
- **Failed:** Testing or inspection demonstrates a defect.
- **Missing:** The required implementation does not exist in the inspected scope.
- **Blocked:** Verification cannot proceed because of a documented limitation.
- **Not applicable:** The requirement genuinely does not apply, with a written justification.

### Rule 6 — Audit first; do not silently change the application

This is an audit-only assignment.

Do not rewrite source files, change architecture, alter database schemas, modify business rules, install new production dependencies, change permissions, migrate databases, or deploy changes during the initial audit.

You may execute safe, non-destructive diagnostic commands and tests.

You may create separate audit artifacts and test reports if the environment permits, without modifying application behavior.

Prepare a prioritized correction plan for approval after the audit. Preserve the existing implementation and record any tests that may affect data or require a controlled environment.

## 3. PHASE ONE — DISCOVER THE ENTIRE PROJECT AND ITS SOURCE MATERIAL

Before judging implementation quality, establish the actual scope.

### 3.1 Inspect the project structure

Inventory the entire accessible project, including relevant:

- Root-level files and folders.
- Frontend applications.
- Backend applications and services.
- Shared components and libraries.
- Application routes and layouts.
- API routes, controllers, handlers, and service layers.
- Authentication and authorization modules.
- Database schemas, models, migrations, seed data, and relationships.
- Background jobs, queues, workers, schedulers, and event handlers.
- Integration adapters and webhook handlers.
- Configuration files and environment-variable templates.
- Static assets, images, icons, fonts, and design tokens.
- State-management modules and data-fetching logic.
- Validation schemas and business-rule modules.
- Unit, integration, API, and end-to-end tests.
- CI/CD pipelines and deployment configuration.
- Logging, error reporting, observability, and audit trails.
- Documentation and architecture diagrams.
- Feature flags, placeholders, mocks, demo data, and temporary implementations.

Inspect hidden project configuration and relevant dependency manifests where accessible.

Do not waste time exhaustively reading generated build artifacts, vendor packages, caches, or dependency directories. Nevertheless, record important exclusions and investigate generated or vendored files when they affect actual runtime behavior, security, or configuration.

### 3.2 Discover the complete blueprint set

Search the workspace and available project resources for all relevant documents and specifications.

Create a document register containing:

| Field | Required information |
|---|---|
| Document ID | Unique reference |
| Filename | Exact filename and location |
| Version | Explicit version, if available |
| Date | Document date, if available |
| Purpose | What it specifies |
| Authority | Approved, draft, historical, or uncertain |
| Conflicts | Related conflicting or superseded requirements |
| Audit use | Requirements or modules covered |

Read the full relevant content of the authoritative blueprint. Do not rely only on summaries, search snippets, or document introductions.

If a document is too large for a single inspection, process it systematically in sections and preserve a coverage register so no sections are inadvertently skipped.

### 3.3 Establish the implementation baseline

Record:

- Current branch and commit, when available.
- Project version and build identifier, when available.
- Frameworks, languages, and dependency versions.
- Available runtime environments.
- Application entry points.
- Available databases and connection modes.
- Authentication providers.
- External integration dependencies.
- Existing automated test coverage.
- Whether a running application can be accessed.
- Any environment limitations that affect audit scope.

Never expose passwords, API keys, private keys, access tokens, or other secrets in the report. Identify their file or configuration location safely, redact their values, and flag inappropriate secret handling.

**Deliverable A:** Complete project inventory, authoritative-document register, and audit-scope statement.

## 7. PHASE FIVE — VERIFY EVERY END-TO-END BUSINESS WORKFLOW

This phase is mandatory and is one of the most important parts of the audit.

Derive the workflow inventory from the blueprint. Do not assume that the presence of individual pages proves that the workflows connecting them are complete.

For each business workflow, create a lifecycle map showing:

**Initiation → Input → Validation → Authorization → Processing → Data persistence → Status transition → Notification → Downstream integration → Final outcome**

Only include stages that the actual business process requires, and identify any additional stages specified by the blueprint.

For every workflow, record:

- Workflow ID.
- Business objective.
- Initiating user role.
- Starting page or event.
- Required input.
- Validation rules.
- Permissions and approval gates.
- Frontend components.
- API calls and backend services.
- Database entities and records affected.
- Status and state transitions.
- Background jobs or event handlers.
- Notifications.
- External systems involved.
- Expected successful outcome.
- Failure behavior.
- Recovery, cancellation, reversal, or retry behavior where required.
- Relevant blueprint requirements.
- Test evidence and final status.

### Required workflow test scenarios

For every applicable workflow, test the following scenarios:

**A. Normal operation**

Execute the entire workflow using the intended user interface and the available backend. Verify the actual final outcome.

**B. Invalid inputs**

Submit missing fields, malformed data, invalid combinations, and out-of-range values where applicable.

**C. Authorization failures**

Attempt prohibited actions using the wrong role or an insufficiently privileged account. Use controlled test accounts and test data.

**D. Processing failures**

Where safely testable, simulate failed requests, unavailable services, rejected transactions, and other relevant failure modes.

**E. Data consistency**

Verify that records, statuses, balances, counters, event histories, and related entities agree after the operation.

**F. Persistence**

Refresh the application, revisit the affected record, and use the permitted data-access layer to establish whether the expected state was actually persisted.

**G. Duplicate submissions and retries**

Check idempotency, duplicate record creation, and retry behavior where relevant.

**H. Lifecycle correctness**

Verify permitted and prohibited status transitions, cancellation, reversal, resubmission, and approval sequences wherever specified.

**I. Multi-user operations**

Where the blueprint involves different users or departments, verify handoffs, assignments, notifications, approvals, and visibility between the appropriate roles.

**J. Downstream processing**

Verify that downstream records, integrations, reports, or events are updated correctly.

Do not mark the complete workflow as passed if only one component has been tested.

For workflows involving money, settlement, ownership, permissions, or other sensitive state, use a safe test environment and explicitly verify the applicable invariants.

**Deliverable E:** End-to-end workflow registry, lifecycle diagrams, scenario results, and workflow-gap report.

## 8. PHASE SIX — AUDIT FRONTEND-TO-BACKEND WIRING

Trace each important user interaction through the full technical stack.

For every significant feature, establish the actual connection:

**UI component → Event handler → State management → API client → Network request → Backend route → Authentication and authorization → Validation → Business service → Database transaction or persistence → Event/notification → API response → UI update**

Verify that the relevant links actually exist and that the request and response contracts agree.

Look specifically for:

- Buttons with empty or incorrect handlers.
- Forms that never call their intended API.
- API clients that point to the wrong endpoint.
- Incorrect HTTP methods or request payloads.
- Missing headers or authentication credentials.
- Mismatched field names and response structures.
- Incorrect error-handling assumptions.
- Stale or incorrectly cached frontend state.
- Failed data invalidation and refresh behavior.
- Database updates that are not transactional when consistency requires it.
- Missing authorization at service or endpoint level.
- APIs that return success before required processing is complete.
- Unhandled asynchronous operations.
- Race conditions and duplicate event handling.
- Timeouts, retry loops, and inadequate retry policies.
- Unused or unreachable backend endpoints.
- Backend features with no corresponding UI entry point.
- Mock services still connected to live user flows.
- Hardcoded IDs, URLs, amounts, statuses, or placeholder results.
- Environment-specific endpoints accidentally used in other environments.
- Fake notification delivery or simulated integration status.

For each finding, record the source and destination of the connection, the specific break or uncertainty, and the test needed to establish correctness.

**Deliverable F:** Frontend-to-backend wiring matrix and disconnected-component report.

## 16. PHASE FOURTEEN — FINDINGS, SEVERITY, AND RISK ASSESSMENT

Assign each finding a unique ID such as AUD-001, AUD-002, and so forth.

Classify severity consistently:

### P0 — Critical

Issues that create an immediate, severe threat to the integrity, security, or safe operation of the platform. Examples may include a confirmed critical authorization bypass, materially incorrect high-impact transaction processing, or severe loss-of-data risk.

### P1 — High

Major blueprint gaps, broken core workflows, significant data-integrity issues, critical integrations that do not work, or other blockers to safe operation or the intended business purpose.

### P2 — Medium

Material functionality gaps, incomplete secondary workflows, significant usability defects, or integration and reliability issues that do not meet P0/P1 criteria.

### P3 — Low

Minor inconsistencies, cosmetic defects, small documentation gaps, or lower-impact improvements.

Severity must be based on actual impact, exploitability where relevant, affected users, business importance, and likelihood—not simply on the number of files affected.

For every finding, provide:

1. Finding ID.
2. Title.
3. Severity and rationale.
4. Affected blueprint requirement IDs.
5. Affected screens, roles, workflows, and integrations.
6. Actual observed behavior.
7. Expected behavior.
8. Evidence, including file paths, function names, relevant lines, logs, or test results.
9. Root cause, if established.
10. Business, technical, security, and operational impact.
11. Recommended correction.
12. Dependencies and prerequisites.
13. Acceptance criteria.
14. Exact retest needed to close the finding.

Separate confirmed defects from suspected issues, specification ambiguities, and findings blocked by unavailable resources.

Do not inflate severity to make the report appear more comprehensive.

### Section 9 — Quality and production-readiness audit

Report automated test outcomes, failed builds, code-quality issues, dependency risks, deployment gaps, observability gaps, and remaining unverified conditions.

List all identified findings with their IDs, severities, evidence, consequences, and recommended fixes.

### Section 11 — Missing and incorrectly implemented blueprint requirements

Provide a requirement-by-requirement account of what is absent, incomplete, contradicted, unreachable, or functionally incorrect.

### Section 12 — Recommended correction plan

Group the required changes into an implementation sequence:

- Stage A: Critical security and data-integrity issues.

- Stage C: Missing or broken core functionality and workflows.
- Stage D: Secondary functions, dashboards, reports, and operational tools.

Reorder stages if dependencies demand it.

Do not modify these files during the audit phase.

### Section 13 — Final go/no-go assessment

Give separate verdicts for:

- Blueprint compliance.
- Functional completeness.
- End-to-end integration.
- Data integrity.
- Security and permissions.
- Test coverage.
- Production readiness.

For each verdict, explain the evidence and outstanding blockers.

A platform must not be described as fully verified merely because it builds successfully or most screens are present.

### Section 14 — Evidence appendix

Include relevant source locations, route and API inventories, executed commands, test logs, browser-test evidence, diagrams, and the full master traceability matrix.

Ensure confidential information is redacted.
